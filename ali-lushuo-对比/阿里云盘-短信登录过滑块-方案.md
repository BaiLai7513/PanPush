# 阿里云盘：短信验证码登录 + 过滑块 —— 可行方案

> 需求：panpush 阿里云盘登录**要走短信验证码**（扫码要第二台设备，麻烦），并且**要能过掉人机校验（滑块）**。
> 本文只讲阿里，给出"为什么会卡"的根因、可落地路线、以及本次从 Voyage APK 里**逆向出的签名算法**。
> 设备基线：OnePlus PKR110 / Android 15 / APatch Root。日期：2026-10-13。

---

## 0. 结论先行

1. **"卡"不是短信的错**——滑块是阿里的**风控（ynuf/无痕验证）**在判断"环境是否像真人/正常客户端"。短信、密码、账号登录都可能被拦。
2. 要让**短信登录能过**，核心是让环境**不被判为风险**。两条路：
   - **路线 A（推荐，成本低）**：WebView 指纹保持一致 + 走**手机版登录页的短信流程**（触摸滑块，手指能正常拖），而不是桌面 UA 的滑块。
   - **路线 B（治本，成本高）**：客户端身份伪装成**官方网页客户端**（请求头），使风控在 API 层就放行。
3. **兜底**：一次性拿到 refresh_token（root 读官方 App / 任意方式登一次），之后 panpush 只做**离线刷新**，彻底不碰登录滑块。

---

## 1. 为什么现在会"卡人机校验"

阿里的登录滑块失败通常=风控给你**打了可疑标签**，导致滑块**拖了也判失败**（不是拖不对）。触发点：

| 可疑信号 | 现状（panpush） | 备注 |
|---|---|---|
| UA 与内核矛盾 | 桌面 UA + Android `Sec-CH-UA-Platform:"Android"` | Client Hints 直接暴露 |
| JS 指纹矛盾 | `navigator.platform=Linux armv8l`、`maxTouchPoints>0`、`plugins=0`、WebGL=Adreno | 一整套"移动端证据" |
| 客户端身份未知 | 通用桌面 Chrome，非阿里已知客户端 | 风控默认从严 |
| 设备未登记 | 无 `device/create_session` | 未登记设备更易被拦 |

> 详见《阿里云盘登录-指纹伪装与移动端布局适配》。**指纹伪装已经写进 `AliyunLoginActivity.kt`，这一步先落地。**

## 2. Voyage 是怎么做的（本次实测/逆向）

### 2.1 它就是 WebView 登录
- `app_webview/Default/IndexedDB/https_www.alipan.com_0.indexeddb.leveldb` 存在 → WebView 打开过 `www.alipan.com`。
- Cookie：`.alipan.com`(SESSIONID/cookie2/_tb_token_/tfstk)、`passport.alipan.com` 上有
  **`last_u_aliyun_drive_web_sms`**（= 用过**短信登录**）、`.ynuf.aliapp.org`(阿里风控 cookie)。

> **这是最重要的旁证：Voyage 走的就是短信登录**，说明"短信流程本身可行"，问题在环境。

### 2.2 登录后做设备登记 + 官方客户端身份
- `POST /users/v1/users/device/create_session`（字符串旁注：「设备校验」），带 `x-device-id` + `x-signature`。
- 阿里 API 请求头：`Origin/Referer: https://www.aliyundrive.com`、
  `X-Canary: client=web,app=adrive,version=v6.8.12`、`Authorization: Bearer`、`x-device-id`、`x-signature`。
- token 续期：`POST /v2/account/token`（`grant_type=refresh_token`）。

### 2.3 UA 是服务端下发的
- OkHttp 拦截器读响应头 **`X-Voyage-Retro-UA`**，用它替换请求 `User-Agent` → UA 不写死。

## 3. 短信登录过滑块 —— 可落地路线（按推荐顺序）

### 路线 A（推荐先试）：指纹一致 + 手机版短信滑块
1. **WebView 指纹伪装**（已实现）：`navigator.platform=Win32`、`maxTouchPoints=0`、plugins 补齐、WebGL 改 Intel、`userAgentData` 改 Windows ……
   —— 目标是让风控**不再给环境打可疑标签**，滑块恢复成"真人一拖就过"。
2. **登录页用手机版流程**：阿里**手机版登录页**的滑块是**触摸滑块**，手指拖动轨迹自然；桌面版滑块在手机指纹里反而容易被判异常。
   - 实测：`pan.xunlei.com/ alipan` 的手机 UA 均 200（阿里手机 UA 未被 302 拦走，与夸克不同）。
3. **短信优先**：登录页里选「短信验证码登录」→ 输手机号 → 获取验证码（若弹滑块，此时环境下应可拖过）→ 输码 → 登录成功。

> 关键：**滑块出现 ≠ 一定过不了**；在指纹一致的真机 WebView 里，用户手指拖拽通常能过。当前"卡"多因指纹被标可疑。

### 路线 B（治本）：API 层冒充官方客户端
在拿到 token 后的所有阿里 API 请求上补齐：
```
Origin:  https://www.aliyundrive.com
Referer: https://www.aliyundrive.com
X-Canary: client=web,app=adrive,version=v6.8.12
x-device-id: <设备id>
x-signature: <见 §5>
```
并可补做 `device/create_session`。→ 让风控把 panpush 当**官方网页客户端**对待。

### 路线 C（最稳，零对抗）：一次性 token + 离线刷新
1. 用任意方式登一次（官方 App / 浏览器 / 短信 / 扫码），拿到 **refresh_token**；
2. 直接 `POST /v2/account/token`（grant_type=refresh_token）换 access_token（panpush 的 `aliyun.py` 已实现）；
3. 之后**再也不碰登录滑块**。

> 备注：root 读官方 App `com.alicloud.databox/databases/0.db` 得到的是 **App 客户端** refresh_token，与网页 client 不通用（已实测）；若走此路，需用**网页登录**产出的 refresh_token，或按 §5 补齐客户端身份。

## 4. WebView 短信登录实现要点

```
加载 https://www.alipan.com/（或直接登录页）
  └─ 指纹伪装注入（onPageStarted/onPageFinished，见 AliyunLoginActivity.kt）
  └─ 用户选「短信验证码登录」→ 输手机号 → 点「获取验证码」
        └─ 如弹滑块：正常触摸拖拽（指纹已一致，应可过）
  └─ 输验证码 → 登录成功
  └─ 读凭证：localStorage.token（含 refresh_token）/ cookie ADRIVE_UID
  └─ 落盘 cred_aliyun + 走 /v2/account/token 刷新
```
判定成功：`localStorage.getItem('token')` 出现且含 `refresh_token`，或 `www.alipan.com` 出现 `ADRIVE_UID` cookie。

## 5. 附录：Voyage 的 `x-signature` 算法（本次逆向，结构已还原）

出处：`classes4.dex`，类 `Liu0;` 方法 `loO`，偏移 `0x316d0c` 起。还原后伪代码：

```text
SALT      = "5dde4e1bdf9e4966b387ba58f4b3fdc3:"
KEYPREFIX = "voyage:alipan:"          // 本 App 的凭证键前缀（对应 cred_aliyun）
h1  = sha256_hex( KEYPREFIX + v15 )          // v15 = user_id（登录后取得）
h1_32 = h1[0:32]                              // 取前 32 个 hex 字符
content = SALT + h1_32 + ":" + v15 + ":0"
digest  = sha256( content )
signature = encode(digest)                    // 以随机 BigInteger 为基做的编码（Lztx.O）
```
- 发送：`x-device-id: <device id>`、`x-signature: <signature>` 到 `/users/v1/users/device/create_session`。
- 固定盐 `5dde4e1bdf9e4966b387ba58f4b3fdc3` 仅出现 **1 次**（全 APK），具 App 特征。

> ⚠️ 说明：该算法**使用了 Voyage 自己的凭证键前缀**（`voyage:alipan:`），因此它更可能是 **Voyage 自有服务**的设备登记签名，而非阿里官方的 `x-signature`。
> 若要用于 panpush，需确认目标端点（`api.aliyundrive.com` 还是 Voyage 自有域名）与最终编码方式。

## 6. 未确认 / 待办（诚实标注）

1. **路线 A 能否让短信滑块通过**：机制推断 + 项目内已有指纹伪装，**未经真机端到端验证**。
2. **阿里短信发送接口是否也带滑块**：登录页由阿里前端驱动，具体风控触发点未抓包确认。
3. **`x-signature` 的最终编码方式**（`Lztx.O(BigInteger,byte[])`）与**目标 base URL**：未完全确认。
4. Voyage 是否**经自有服务端代理**阿里 API：未确认（`voyage:alipan:` 前缀 + 自有盐提示"可能有自建服务"）。
5. 所有结论基于 **APK 静态分析 + 本机数据实测**，**未含真实登录抓包**。

---

## 7. 一句话给决策

> **先走路线 A**：把已写好的指纹伪装放进 `AliyunLoginActivity.kt`，登录页走**手机版短信流程**，让用户正常拖滑块即可过；
> **若仍被拦**，再上路线 B（官方客户端头 + `create_session`）；
> **要绝对稳定**，用路线 C（一次性 refresh_token + 离线刷新），彻底绕开登录滑块。
