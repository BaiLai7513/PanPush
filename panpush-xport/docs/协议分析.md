## 三、签名机制（本次核心发现）

### 1. 网页端真实配置（`utils-initial.js` 模块31）

```jsonc
"pan.xunlei.com": {
  "clientId":      "Xqp0kJBXWhwaTpB6",   // 与参考实现相同，仍有效
  "packageName":   "pan.xunlei.com",
  "signKey":       "k&&9(rT5LU",
  "algVersion":    "1",
  "funName":       "pubqKytV9pQyXvHAKg2SfabUzJeb1FtK4Rg",
  "funFile":       "code-res"
}
```

### 2. 版本号：`1.92.89` → **`1.93.8`**（参考实现用的是老版本）

### 3. 两种机制，按 `funFile` 分流

```js// utils-async.js 模块1641
_ = clientId + version + host + deviceId + timestamp
if (!A()) {                                  // pan.xunlei.com 走这里（funFile="code-res"）
  j = await getPubKeySignUtil("code-res", funName)
  _ = j(_)
} else {                                     // 盐链（老机制）
  algorithms.forEach(a => _ = md5(_ + a.salt))
}
_ = "1." + _
```

- 盐链来源：`https://risk-account-ssl.office.k8s.xunlei.cn/amaze/v1.0/algorithms`
  - ⚠️ 本网络**不可达**（直连与代理均超时）
  - 且 `pan.xunlei.com` 的 `funFile=code-res` **不走这条路**
- **参考实现 = 老机制（盐链）**，所以现在必然失败。

### 4. 新机制 = 白盒混淆

- 签名原语确认：模块0（`app.dc02…js`）= **标准 JS MD5**（含 HMAC），`md5hex(x)` 可用。
- 但每个 `pub*` 函数都是：

```jsfunction X(e) {
  var n = t(0);                    // md5
  var r = "Rxrg";                  // 每函数一个随机盐
  var o = t(13).pub9bJh8o0…,       // 再跳到另一个混淆函数
      c = t(12).pubM990C0…;
  return o(n(e + r)) || c(n(e + r));   // 双路试探，取真值
}
```

- 调用图**跨模块自引用**（模块13 引用 `t(13)` 自身），是刻意构造的反逆向迷宫。
- 因此**手写移植不现实**；要复现只能在 JS 环境里**执行**它。

## 七、【重大更新】root 直读 APP 方案（已实测打通 ✅）

**不需要复现白盒签名** —— 直接从 APP 私有目录取现成凭据即可。

### 凭据来源

| 用途 | 文件 | 键 |
|---|---|---|
| `Authorization` | `shared_prefs/auth_pref.xml` | `credentials_Xp6vsxz_7IYVw2BB` → JSON 里的 `access_token`（Bearer JWT，2h 有效，APP 自己会刷新） |
| `X-Captcha-Token` | `shared_prefs/xl-acc-captcha-token.xml` | `*captchatoken`（`ck0.` 前缀） |
| `X-Device-Id` | `__device_info_new__.xml` | `device_id_new` = `34068a3cec7abb281388182709f8ae3c` ← **必须用它**，令牌里绑定了它 |

### 实测结果

```
GET /drive/v1/files  → 200 ✅（返回真实云盘列表）
GET /drive/v1/share  → 400 "share_id invalid"（说明 captcha/auth 均已通过）```

- 带错设备 ID → `captcha_invalid: device not match`
- 不带 captcha → `captcha_invalid: captcha_token is empty`（**captcha 强制**，无法省略）
- **captcha 令牌过期 316s 仍可用，且可重复使用**（服务端不严格校验有效期）
- APP 与 WEB 的 client_id 都能用（`Xp6vsxz_7IYVw2BB` / `Xqp0kJBXWhwaTpB6`）

### 结论

- ✅ 迅雷接入**可行**，且比预想简单得多：**root 现场读取即可**，无需 Node 沙箱、无需逆向混淆。
- ⚠️ 依赖 APP 至少登录过一次且缓存里存在 captcha 令牌；若被清掉则需先打开 APP 触发一次。
- 📌 读操作全通；转存（`/share/restore`）仍未测（写操作，需真实分享链接 + 小文件）。

## 八、分享直链 vs 个人云盘直链：限速对比（2026-10-11 实测）

### 重要修正：captcha 令牌有 TTL，且只在触发特定页面时刷新

- 令牌 `expiresat` 是**毫秒**时间戳，键名 `captchatoken` 长度是 **12**（`k[:-12]` 才是前缀；
  用 `[:-11]` 会取错前缀 → 排序失效 → 一直用旧令牌）。
- 令牌**寿命只有几分钟**。过期后：
  - `GET /files`（列表）**仍然 200**（宽松）；
  - `GET /files/{id}?usage=CONSUME`（取直链）**400 `captcha_invalid`**（严格）。
- **刷新触发条件**：仅**启动 APP 首页不会刷新**；必须让 APP 处理一次**分享深链**或进入
  下载相关页面，才会申请新令牌。
  实测命令（root）：
  ```
  am start --user 0 -a android.intent.action.VIEW \
    -d 'https://pan.xunlei.com/s/<SHARE_ID>?pwd=<PWD>'
  ```
  约 10 秒后 `xl-acc-captcha-token.xml` 出现新条目（实测从 3 个变 4 个，新令牌 +243s）。
- ⚠️ 工程含义：`XunleiParser` 取直链前应**校验令牌新鲜度**；过期则提示用户打开一次迅雷 APP
  （或由脚本自动 `am start` 分享深链触发，再重读）。

### 限速对比（同一文件：`Smart Tool v3.0.exe` 45.9 MB）

| 路径 | host | 1 连接 | 4 连接 | 16 连接 |
|---|---|---|---|---|
| **分享直链**（`/share/file_info`） | `vod0100-h04-vip-lixian` | 0.14 | 0.54 | **0.69 MB/s** |
| **个人云盘直链**（`/files/{id}?usage=CONSUME`） | `vod0095-h04-vip-lixian` | **5.88** | 5.76 | 4.81 MB/s |

（单位 MB/s；个人云盘 1 连接即跑满 ~49 Mbps，16 连接那条只是提前跑完切片，非降速。）

### 结论

- **限速发生在「分享访问路径」上，不在 CDN 主机上**：两者 host 都是 `*-vip-lixian.xunlei.com`，
  但分享链被服务端按来源限到 ~6 Mbps，个人云盘链不受限（~48 Mbps），**相差约 8.5×**。
- 因此：**能走个人云盘路径就别走分享路径**。分享链的价值仅在"解析别人的分享文件"；
  若是自己网盘里的文件（或转存后），应改用 `/files/{id}?usage=CONSUME` 取链。
- 推送 Gopeed 时对分享链：`connections` 给 8~16 可缓解（4 连已达 78%）；对个人云盘链：
  `connections` 1~4 即可，多连接无益。
- 直链下载**必须** `User-Agent: okhttp/4.9.0`（否则 403）。
